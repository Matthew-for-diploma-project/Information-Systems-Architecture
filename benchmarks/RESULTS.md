# Замеры реплик: вариант по примеру lab5

Измерения выполнены на Temurin OpenJDK 23.0.1+11, Linux x86_64, 9 доступных процессоров по affinity среды. Ресурсы общие.
Запускались отдельные JVM: один database и по 1/2/3 реплики выбранного слоя, остальные по одной. Heap каждой JVM: 16–96 MiB.
Это настоящие отдельные процессы с TCP, protobuf и JDBC over TCP, но не Docker-контейнеры. Docker Engine недоступен.

Нагрузка: 12 клиентов, по 5 чтений METRICS прогрева, затем 600 измеряемых чтений суммарно. Запись сообщений не измерялась.
Каждая из 9 комбинаций выполнена 3 раза в перемешанном порядке (seed 2026 + номер повтора). В 27 прогонах ошибок нет. Проверено число живых реплик; после нагрузки счётчики остались нулевыми — данные не менялись.

## Сравнение

- facade: 1 → 2 → 3 реплики дали 336.1 → 350.1 → 371.7 запросов/с; отношение к одной реплике: 1.04x и 1.11x.
- business: 1 → 2 → 3 реплики дали 412.4 → 246.2 → 413.9 запросов/с; отношение к одной реплике: 0.60x и 1.00x.
- storage: 1 → 2 → 3 реплики дали 307.7 → 217.6 → 247.6 запросов/с; отношение к одной реплике: 0.71x и 0.80x.

Линейного роста не наблюдается. Реплики делят ресурсы одного компьютера, данные хранятся в единственном H2-процессе; каждый запрос проходит сетевые переходы и открывает JDBC-соединение. У записи дополнительно есть общая блокировка строки транзакции. Это архитектурные ограничения, а не основание ожидать ускорение в 2/3 раза.

Разброс коротких прогонов заметен: небольшую разницу медиан нельзя выдавать за доказанный устойчивый выигрыш. Измерение чтения METRICS не доказывает такую же производительность SEND или обработки больших историй.

На Windows скрипт `powershell -ExecutionPolicy Bypass -File .\benchmark.ps1` выполняет 9 комбинаций именно Docker-реплик, проверяет их число и сохраняет новый benchmark-results.csv и benchmark-comparison.md. Один запуск скрипта — один проход всех комбинаций. Эти новые файлы не заменяют сохранённые measured.csv.
