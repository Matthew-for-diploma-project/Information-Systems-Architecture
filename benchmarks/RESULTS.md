# Результаты замеров лабораторной №5

Реальное выполнение BenchmarkMain на OpenJDK 23.0.1+11 (Temurin), Linux amd64.
Среда сообщает 9 доступных логических процессоров; они не считаются выделенными исключительно этому замеру.
Три отдельных JVM-процесса, TCP через loopback, H2 WRITE_DELAY=0; heap каждого процесса 32–128 MiB.
8 клиентов, 5 SEND прогрева на клиента и 50 измеряемых SEND на клиента; 400 операций на повтор.
По 3 повтора для каждой из 8 конфигураций. В каждой строке ниже — медиана трёх повторов.
Ошибок в 24 прогонах нет; после каждого сверены история и счётчики.

## Сравнение

Для отдельного компонента сравниваются его 1, 2 и 4 обработчика при неизменных четырёх обработчиках остальных слоёв. Точка all-4 общая для трёх сравнений. baseline показывает весь конвейер с одним обработчиком на слой.

- Фасад: при переходе от 1 к 4 обработчикам медиана 143.1 → 155.6 запросов/с (+8.8%).
- Прикладная логика: при переходе от 1 к 4 обработчикам медиана 179.6 → 155.6 запросов/с (-13.3%).
- Хранилище: при переходе от 1 к 4 обработчикам медиана 215.2 → 155.6 запросов/с (-27.7%).

В этом запуске два обработчика фасада и логики дали более высокую медиану, чем четыре; у хранилища лучшая медиана была с одним обработчиком. Это наблюдение короткого опыта, а не универсальная рекомендация настройки.

Увеличение числа обработчиков не обеспечивает линейного ускорения. В хранилище одно общее JDBC-соединение и последовательная транзакция под ReentrantLock: дополнительные потоки не превращают запись в H2 в параллельную. Прикладной слой также ожидает несколько внутренних RPC внутри транзакции. Эти ограничения объясняются кодом; сам короткий замер не позволяет отделить их вклад от стоимости сокетов, fsync и планирования потоков.

Варьируется число обработчиков процессов, а не число реплик или CPU-квота Docker. Это измерение полного пути запроса; результаты не следует выдавать за микробенчмарк одной сериализации protobuf или за замер трёх контейнеров на разных узлах. Нагрузка небольшая, прогрев короткий, среда общая. Для сравнения другой машины нужно повторить все конфигурации, сохранив нагрузку и параметры JVM.

## Исходные данные и воспроизведение

- [24 исходных строки CSV](measured.csv)
- [Параметры фактической среды](measured-environment.txt)

```powershell
java -jar target/chat.jar benchmark benchmarks/scaling.csv 3 8 50
```

Либо после сборки образа:

```powershell
docker compose run --rm benchmark
```

Новый запуск пишет scaling.csv, не изменяя versioned measured.csv. В контейнерном варианте benchmark сам запускает три JVM внутри одного контейнера; рабочая БД сервиса storage не затрагивается. Приложение не выводит отчёт в консоль.
